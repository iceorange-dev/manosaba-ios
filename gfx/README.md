# gfx — graphics layer (NVN → Metal)

Switch games draw with NVN, the console's native graphics API. This layer reimplements NVN on Apple's Metal: every NVN call the game makes lands
here, is recorded as a command, and is replayed as Metal commands at submit time. Shaders are never translated at run time (iOS has no JIT for
them anyway): they are translated offline, once, into Metal libraries.

## How it works

### Taking over NVN

- A game imports one NVN symbol, `nvnBootstrapLoader`, and fetches every other NVN function through it by name. The host takes over that import
  (`nvn/hle_nvn.c`); none of the console's graphics driver runs.
- `nvn/names.txt` lists the 523 names the layer knows. Each has a thunk (`nvn/nvn_thunks.S`, generated) that counts the call and jumps to the
  implementation. 262 names are implemented with the `NVN(...)` macro; the others go to a stub that logs
  `[red] unimplemented NVN function called: <name>`. A name not in `names.txt` returns NULL and logs `[red] NVN address lookup of unknown name: <name>`.
- Every implementation is checked at compile time against `nvn/nvn_protos.h` (generated by `tools/gen_protos.py` from `nvn/include/nvn.h`).
  Apple arm64 and the Switch differ for integer arguments narrower than 32 bits, so `NVNboolean` parameters are received as `uint32_t` and only the
  low 8 bits are read.
- Object layouts: the host keeps its objects inside the memory the game allocates for NVN objects (`nvn/nvn_obj.h`, with a static assertion per
  object against the size the game reserves). The community `nvn.h` headers describe older SDKs; sizes were checked against how the game actually
  uses each object (for example Unity copies NVN objects by value).

### Record and replay

- **Interface layer `nvn/hle_nvn.c`** with its parts in `nvn/hle/`: object implementations, and recording of command buffer calls into the command
  memory the game provides.
- **Replay layer `nvn/nvn_mtl.m`** with its parts in `nvn/mtl/`: replays the records as Metal commands at submit time.
  - The decisions that need no Metal are moving to `nvn/core/` (plan item 264): plain C modules, each its own translation unit with a header,
    for a second backend (Vulkan) to share. What a module needs of the backend its header declares ("The backend provides"). The replay
    loop is there too (`nvn/core/exec.c`); each command it does not keep itself it hands to the backend through `nvn/nvn_backend.h`.
  - The Android host runs the same interface layer and core on Android's backends: under adb the null one (`nvn/null/null.c`, plan item 301c), a
    GPU that draws nothing and finishes each submission when it is committed, its event writes and counter reports landing then (its file lists
    every function a backend provides); in the app the Vulkan one (`nvn/vk/`, plan item 301e: pools placed at their own addresses, submissions
    fenced by a timeline semaphore, textures, copies, clears, draws with the game's shaders from a Vulkan bundle of the same translation
    (`tools/dmsh_vk.py`, plan item 301e2), presents).
  - Memory pools become zero-copy `MTLBuffer`s on the game's memory; GPU address = CPU address, so only unified-memory devices are supported.
  - GPU completion effects (sync objects, events, counters) become visible only after the Metal command buffer has completed.
  - Pipeline and depth-stencil states are cached by state hash.
  - Textures in Tegra block-linear layout are deswizzled before upload (see [tex/README.md](tex/README.md)).
  - Presentation: the game's swapchain texture is drawn to a `CAMetalLayer`, paced by `nvn/nvn_pace.h`.

[nvn_metal_mapping.md](nvn_metal_mapping.md) lists where each NVN object and command lands in Metal.

## Shaders

A game's shaders are Maxwell (Tegra X1) machine code. Each one is identified by a **key**: the first 16 hex digits of the sha256 of its 0x880-byte
control section followed by its code area (the length at control +0x704). At run time the game passes both to `nvnProgramSetShaders`, and the
replay layer computes the same key (`shader_key` in `nvn/hle/programs.inc`; the same definition as nxnative's). The control section alone is not
enough: it holds sizes and resource counts but no hash of the code, and in Tears of the Kingdom 807 of 3667 shaders share their control section
with another shader (313 sections), so a key without the code ran one shader's code for all of them.

```
capture  (<key>.ctl + <key>.data per shader)
  ├─ tools/shmap_from_capture.py   → shader stage map   (<key> TAB vs|ps|cs; DM_NVN_SHMAP)
  └─ tools/dmsh_build.py
       dmsh_xlate (Ryujinx shader translator, C#)   → SPIR-V
       spirv-cross                                  → MSL
       xcrun metal / metallib                       → <cache root>/b-<V>/<key>_b.metallib + <key>_b.json
  tools/c1_guard.py <cache>/b-<V>                   → c1 list (read next to the stage map)
  tools/dmsh_vk.py   (dmsh_build.py's jobs, SPIR-V kept for Vulkan)   → <game>.dmvk, the Android app's bundle (DM_VK_SHADERS)
```

- **Capture**: either the host writes every shader the game creates (`DM_SHDUMP=<dir>`; run it with an empty stage map the first time), or an
  engine extractor reads them from the game files without running it (`engines/unity/shader_extract.py`). Static extraction is complete;
  run-time capture only has the shaders the run reached.
- **Outputs** in `b-<V>/`: `<key>_b.metallib`, `<key>_b.json` (reflection used at replay: each binding's kind, slot and argument index),
  `<key>_b.metal` (MSL), and for some fragment shaders `<key>_bf.metallib`, a framebuffer-fetch ("readable tile") variant used to merge passes
  (`tools/dmsh_fetch.py`). `IOSOUT=<dir>` also builds iphoneos libraries into `<dir>/b-<V>/` (`tools/ios_metal.py`).
- **Chain version V**: 12 hex digits hashing the chain's sources, options and tool fingerprints (`tools/dmsh_chain.py`, `tools/dmsh_chain.lock`).
  The host takes V from `nvn/dmsh_chain.h`, loads only from `b-<V>/` and checks V in every JSON. After changing a chain file or a tool:
  rebuild `tools/dmsh_xlate` if its sources changed, `dmsh_chain.py --update-lock` (tools) / `--header`, then `dmsh_build.py`, `c1_guard.py`,
  and rebuild the host.
- **c1 list**: shaders whose index into their built-in constant section c1 could not be proven bounded; each gets its own 64 KiB c1 buffer.
- **Vulkan bundle** (plan item 301e2): `tools/dmsh_vk.py <capture dir> <out>` (DM_GAME, DM_ROOT) translates the same jobs to SPIR-V, moves
  each stage's bindings so a program's two stages share one descriptor set (pixel +64), adds the reflection the Vulkan backend binds by
  (`nvn/vk/vk_shader.c`) and checks every module with the NDK's spirv-val; one file, carried in the APK (android/Makefile `SHADERS`). It
  takes dmsh_build.py's functions as they are and is not part of the chain version (the Metal chain does not change with it).
  Without a list matching V, every shader is treated that way (and a red line says so).

Binding conventions used by the translation:

- uniform buffer slot r is constant section `c[3 + r]`;
- the handle of texture r is at `c[2][tex + 8r]`, of separate sampler r at `c[2][samp + 8r]`, of image r at `c[2][img + 8r]`, with the bases of
  the game's `nvn_c2` (manosaba: 0x168 / 0x568 / 0x120; Tears of the Kingdom: 0x20 / 0x568 / 0x120);
- the depth convention is the game's `depth_mode`: with `near_is_minus_w` every vertex shader remaps z to Metal's 0..w;
- the address of storage buffer r is at `c[0][base + 16r]`, base: vertex 0x110, compute 0x310, fragment 0x510;
- compute thread group size: control section +0x748 / +0x74c / +0x750;
- window origin top left (same as Metal): nothing is flipped.

## Tests

```sh
make -C gfx/tests run       # needs a Metal device; a few tests run under MTL_DEBUG_LAYER=1
make -C gfx/tex/tests run
```

The tests compile the production sources in directly and read no game data. `t_nvn` drives the interface layer the way a game does, from
`nvnBootstrapLoader` to presentation; the `.m` tests compile the replay layer and check its pass optimizations (`t_reorder_chain`, `t_defer_chain`,
`t_fuse_check`, `t_zskip`, `t_xv`, `t_view_levels`, …), presentation cropping, mip extents, sRGB views and GPU deswizzling. The `t_core_*.c`
tests check `nvn/core/` without a GPU: each links all its modules, the backend's hooks as weak defaults it overrides where it needs to
(`tests/core_fakes.c`) and the shared checks (`tests/core_test.h`); `t_null_be.c` checks the null backend on its own.

## Run-time switches

All are environment variables. The Mac host fills `DM_NVN_SHMAP` and `DM_MSL_DIR` from the game profile; the iOS app sets them itself.

| Switch | Effect |
|---|---|
| `DM_NVN_SHMAP=<file>` | Shader stage map (required). `c1_full.tsv` and an optional `pso_manifest.tsv` are read from the same directory |
| `DM_MSL_DIR=<dir>` | Shader library root; libraries are loaded from `<dir>/b-<V>/` |
| `DM_SHDUMP=<dir>` | Capture every shader the game creates (`<key>.ctl` / `<key>.data`) |
| `DM_PSO_RECORD=<file>` | Append the pipelines used in this run (format of `pso_manifest.tsv`, the optional background warm-up list) |
| `DM_PSO_MANIFEST=<file>` or `off` | Use another warm-up list, or none. By default the warm-up reads `pso_manifest.tsv` next to the shader map and the player's own list, whichever exist |
| `DM_PSO_USER=<file>` | The player's own list: pipelines and shaders built on the submit thread are appended to it and warmed at the next launch (default `pso_user.tsv` beside the save directory) |
| `DM_NVN_LOG=1` | Log NVN object creation |
| `DM_NVN_FRAMES=N` | Print the per-frame call table for the first N frames (default 3) |
| `DM_NVN_TSV=<file>` | Per-frame call table and timings as TSV (`DM_NVN_TSV_CALLS=0`: timings only) |
| `DM_SLOWFRAME=1` | Log a timing breakdown only for frames that were late |
| `DM_NVN_SHOT=<frame>[,<frame>…]:<path>` | Save the presented picture at those frames (`%d` = frame number) |
| `DM_NVN_SHOT_OUT=<W>x<H>` | Screenshots capture the picture after scaling to that size |
| `DM_NVN_TEXDUMP=<frame>:<path>` | Save every color render target of that frame |
| `DM_NVN_TEXSNAP=<index>,<a>-<b>,@<W>x<H>` | With `DM_NVN_TEXDUMP`: also save the color attachments of those render passes of that frame right after each pass (in-frame index, index range, or every pass with an attachment of that size; at most 96). The copy runs on the replay's own blit encoder, so it sees what the pass left; the pass dump prints `S <pass> snapshot index <i>`. With `DM_NVN_TBDR=0` no attachment store is elided |
| `DM_NVN_TEXNZ=1` | Pass dump: for each texture binding, the share of non-zero words in its guest storage, and for BC textures in the Metal texture's level 0 (does the content reach Metal?) |
| `DM_NVN_TEXCLASS=1` | Log each GPU-only texture at creation: texture flags, pool flags, how much of its storage the CPU filled |
| `DM_NVN_UBLOG=1` | Log the raw arguments of every `UpdateUniformBuffer` and `BindUniformBuffer` call |
| `DM_NVN_REUPLOG=<n>` | Log the first n re-uploads of memory-backed textures (which textures does the CPU keep rewriting?) |
| `DM_NVN_PASSDUMP=<frame>` or `<a>-<b>` | Log each render pass (attachments, loads / stores, samples) for those frames to stderr; `DM_NVN_PASSDUMP_ALL=1` adds every draw |
| `DM_NVN_PROF=1` | Time every implemented NVN function |
| `DM_NVN_PASSGPU=<file>` | GPU time of each render pass and dispatch as TSV (timestamps: an `MTL4CounterHeap` on Metal 4, stage-boundary samples on Metal 3); every 300 frames a line with the GPU time a frame and the kinds of pass that took the most |
| `DM_NVN_PASSGPU_EVERY=<n>`, `DM_NVN_PASSGPU_FROM=<frame>`, `DM_NVN_PASSGPU_FRAMES=<n>` | With `DM_NVN_PASSGPU`: time every nth submission only, and none before that frame or from n frames after it (plan item 256: the iPhone's first minute runs on burst power) |
| `DM_RT_PEAK=1` | The real-time computation declared for the per-frame threads covers 1.1 x each 120-frame window's longest frame too (plan item 248; measured worse on the iPhone, off) |
| `DM_NVN_TEXCENSUS=1` | One line per new texture shape of the kinds whose layout or sampling rules came from outside checks: cube arrays, LINEAR_RENDER_TARGET without LINEAR, MINIMAL_LAYOUT, packaged 3D, linear block-compressed, formats with their own swizzle (sampled or as render targets) |
| `DM_NVN_WB_IDLE=1` | An experiment (plan item 94): a texture the GPU wrote in a CPU-visible pool and left alone for 30 submissions is written back to its storage, and one whose storage the CPU writes afterwards is uploaded from it again. Off: it changes more than the terrain it is for (94a) |
| `DM_NVN_WB_IDLE_SUBS=<n>` | With `DM_NVN_WB_IDLE=1`: write back after n idle submissions instead of 30 (1: after every GPU write; a diagnostic) |
| `DM_NVN_ANISO=<2..16>` | Anisotropic filtering raised to that on mipmapped linear samplers without a depth compare or a reduction (most of Tears of the Kingdom's ask for 1); off by default, which keeps the shots comparable with the console's |
| `DM_NVN_COUNTS=1` | Counters in the power summary: draws sampling their own attachment, timestamp reports, ClearTexture, passes without a draw, passes drawing only a top-left part, counter reads and svcs a second |
| `DM_NVN_TS_LATE_US=<µs>` | Report counter timestamps that much later (the game sees a slower GPU) |
| `DM_FPS_TRIAL=1` | Frame-rate trials (plan item 216, `nvn/nvn_fptrial.h`; off by default: on the iPhone 17 Pro at 60 Hz none of 22 held on Great Sky Island). A game whose step the host sets (Tears of the Kingdom with the option realtime), held at interval 2 or 3 for 5 s while the player's target is 60, reads its counter times drawn nearer their submission's GPU start (× 0.35) until it picks interval 1 and for 1 s after, so the GPU's clock can come up; a game that steps back up within 4 s on the real times has failed, and the wait doubles (up to 32 s). Only at a 60 Hz present rate in game interval mode |
| `DM_NVN_TS_DVFS=<x>` | A diagnostic for a Mac: report times x times further apart once the game has held interval 2 or 3 for 1 s, the real times 0.5 s after it picks interval 1, as an iPhone's GPU clock follows the frame rate |
| `DM_FRAME_STEP=vsync` | The host paces the frames (plan items 133, 222, `nvn/nvn_fstep.h`) for a game whose step the host sets: each frame stays k vsyncs of 60 Hz, three late frames step up, frames that fit k − 1 try it, and the game steps the time shown; its own present interval is not used for pacing |
| `DM_FSTEP_OPT=0` | With `DM_FRAME_STEP=vsync`: no trial of k − 1 whatever the cost (plan item 222). By default one starts after 5 s at k above its minimum, its first second not counted late while the GPU clock comes up; a failed one doubles the wait (up to 32 s) |

| `DM_GFXUSE=<file>[:<frame>]` | Record the guest memory ranges the GPU reads over 30 frames |
| `DM_NVN_TBDR=0` | Turn off all pass optimizations (attach, load and store everything), for equivalence comparisons |
| `DM_NVN_TBDR_OFF=<part>[,<part>...]` | With the pass optimizations on, keep the parts named off: `zskip`, `xv`, `cover`, `store`, `sdx`, `defer`, `fuse`, `hoist`, `ds`, `cont`, `rtheap`, or `all` (plan item 62j). | `DM_NVN_CHUNK_DRAWS=<n>`, `DM_NVN_CHUNK_FIRST=<n>` | Mid-submission commits: the work encoded so far goes to the GPU as a command buffer of its own after the first `DM_NVN_CHUNK_FIRST` draws (default 60), then every `DM_NVN_CHUNK_DRAWS` draws (default 75); either at 0 turns them off |
| `DM_NVN_NOCULL=1` | Draw with face culling off (does a missing draw come back?) |

## Known limitations

Paths that are not implemented log a red line once when reached (`RED_ONCE`, `nvn/core/core.h`): clears in the middle of a render pass and color
clears with a partial mask or scissor; indexed quads and 8-bit indices; some texture-to-texture copies and texture clears.

The functions in `g_nops` (`nvn/hle/nops.inc`), such as `MultiDraw*IndirectCount`, `DispatchComputeIndirect`, `SetDepthBounds` and
`DownsampleTextureView`, do nothing and log nothing.
